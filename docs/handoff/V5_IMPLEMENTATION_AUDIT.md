## Persistence architecture and trust

Commit history and blobs live in Git objects; branches in Git refs. Workspace manifests and worktree metadata, checkpoint Git objects and refs, submission manifests and candidate commits/refs/worktrees are durable coordination metadata but mutable and unauthenticated. Conflict simulation uses temporary objects and ephemeral reports. Dependency graphs are recomputed and tied to source snapshots; watcher events are in-memory and lossy. Identity/credentials and protected audit have no production persistence until storage/security prerequisites are independently validated. Git repositories, refs, file ownership and worktrees are not authenticated actor identity, protected audit, an execution boundary, or a filesystem sandbox. Do not place credentials in them.

## Workspace provisioning intent (V5)

`Git::workspace_create` now CAS-writes a versioned `refs/rit/operations/<uuid>` intent before workspace metadata/branch/path creation, then records manifest, branch, exclusive directory, worktree and verification steps and completion. A killed process can leave actual Git or filesystem state ahead of its last recorded step; refs are unauthenticated coordination data, not atomic transaction logs. Failure evidence is best-effort, never a basis to delete or blindly replay. `WorkspaceService::operations` / `rit workspace operations --repo ...` compares the record with actual manifests, branch refs and worktree inventory. `rit workspace reconcile --repair` only CAS-marks an already-matching ready/no-checkout workspace intent complete; it does not modify workspace files, branches or admin metadata. Mismatches and missing content require manual review. Legacy V4 workspaces have no retroactive operation records. `workspace_intent_survives_killed_rit_and_repair_only_finalizes_matching_metadata` actually SIGKILLs the RIT process after path reservation via a fixture Git wrapper, verifies the pending intent/branch/directory survive restart, verifies metadata-only repair does not clean it up, and tests a simulated missing final intent update. Race/fault injection at every boundary, moved/missing worktree recovery and removal remain open.

## Captured-subset recovery into a new worktree (V5)

`GitCheckpointService::restore_plan/restore_new/restores`, `Git::checkpoint_restore_*`, and `rit checkpoint restore ID --repo REPO --to NEW_PATH --preview` now support an intentionally limited **non-destructive new-destination** recovery. Apply additionally requires `--yes --accept-incomplete`; an existing destination and existing-workspace restore remain disabled. A nonexistent new destination has no preexisting data to protect, so no pre-restore checkpoint is made; no existing workspace is touched. The plan verifies Git fsck, checkpoint structure, raw index against enumerated stages via a temporary index, rejects gitlinks and split indexes, checks path overlap and bounds, and lists exact created/deleted paths. Plan verification creates a temporary index but no workspace or refs.

Apply creates a CAS-backed `refs/rit/restores/<id>/manifest` intent and checkpoint-retention ref, reserves a private empty directory, registers a detached `--no-checkout` Git worktree at the captured base, recreates regular files and symlinks with no-follow/exclusive descriptor-relative operations, and installs the raw index using an exclusive `index.lock` and Linux `renameat2(RENAME_NOREPLACE)`. Per-path CAS updates report attempted and completed entries. It rereads captured bytes/modes/links and index once before completion. No Git checkout, hook, filter, script, merge driver or restore into a preexisting directory is used. Symlink targets are restored verbatim and may point outside the new worktree; RIT does not follow them. An interruption or collision can leave a worktree, directory, partial files, intent or owned index lock; `checkpoint restores` reports current Git inventory and the last known step. There is **no automatic resume, deletion, rollback or claim of power-loss transaction durability**. Same-UID concurrent filesystem interference and post-verification changes cannot be excluded; metadata is unauthenticated and no filesystem sandbox is claimed.

Recovery recreates only data the checkpoint actually captured. Every checkpoint remains `complete=false`: omitted untracked/ignored files, uninitialized or dirty submodule content, LFS payloads, full POSIX metadata, Git merge/rebase operation metadata and atomic cross-file state are not recoverable. Restore rejects submodule/gitlink index entries and split-index snapshots rather than pretending to recover them; LFS pointers, if present, are just captured bytes. No partial `--keep`, general in-place restore, file-size limit configuration, streaming or fully recoverable checkpoint claim is made.

New schema-2 captures reread/hash each selected path and re-enumerate explicitly included untracked files, then recheck original index and HEAD; a detected change aborts without changing the workspace or existing refs and identifies the path. `consistency=observed_quiescence_on_recheck` does **not** mean an atomic snapshot: a change can occur between observations or be reverted, and the source can change immediately afterwards. Schema-1 V4 manifests remain readable as `not_recorded`. Original index is never modified or locked by capture; concurrent index changes are detected by bytes-before/after but this is not a transactional snapshot.

Tests: `checkpoint_recovers_captured_subset_to_new_worktree_without_overwriting_newer_source` checks preview/confirmation, staged and unstaged bytes, ignored/untracked content, deletion, symlink, executable bit, exact raw index, newer original work preservation and hook non-execution. `checkpoint_preserves_unmerged_index_deletion_and_refuses_large_files` additionally restores stages 1–3 into a fresh worktree. `restore_refuses_concurrently_created_destination_file_and_retains_intent` injects a collision and verifies newer content survives; `restore_intent_survives_kill_before_worktree_creation_without_cleanup` actually kills RIT and checks persisted intent/directory. `checkpoint_refuses_concurrent_file_change_without_reverting_it` injects a source change and checks refusal, original index and newer bytes. Further adversarial, cross-platform and fault-injection review remains essential.

## Submission lifecycle and candidate interruption evidence (V5)

Schema-2 Git submission manifests add an untrusted creation timestamp and cooperative `submitted`/`cancelled` state; schema-1 V4 manifests remain readable. `rit submit` is an app-service-backed alias for creation. `submission cancel` CAS-updates only the manifest and leaves source, target, candidate refs, candidate directories and user files intact; cancellation prevents later candidate requests in ordinary sequential use. `submission reconcile` correlates submissions with candidate inventory and reports source/target staleness or unavailable inspection. These are not authenticated review or approval states; draft/review/rejection/expiration workflows remain unimplemented. Cancellation and candidate creation span independent Git refs and are **not one atomic transaction**: concurrent cancellation can race candidate creation, and no security claim depends on either.

Candidate provisioning now records CAS steps (`provisioning`, `commit_reserved`, `directory_created`, `worktree_created`, `worktree_verified`, then `ready`/`no_checkout`); recorded state may lag actual filesystem operations after a crash. `rit integration list/inspect/reconcile/validate` shares `SubmissionService`, observes actual inventory and stale target, reruns bounded Git fsck and partial dependency analysis, and explicitly reports repository builds/tests `NOT_RUN` and publication unavailable. `integration cleanup` stays disabled, and interrupted candidates are never automatically removed or replayed. The SIGKILL test `interrupted_candidate_is_discoverable_and_cancel_preserves_all_work` leaves a real candidate ref and directory after killing RIT before worktree addition, verifies them after restart, cancels the submission, refuses a later candidate and preserves an independently added file and original source/target refs. This is detection and safe preservation, **not** complete automatic candidate recovery. Candidate validation is ephemeral, not protected audit.

## Reconciliation transition evidence and MCP views (V5)

`activity::compare_snapshots` compares actual Git inventory, HEAD OIDs, branch attachment, lock flags, and index XY status between two successfully observed endpoint snapshots. The native watch CLI emits these bounded transitions with every Git reconciliation; it never infers an actor, command, or complete intermediate sequence. Unavailable status does not generate fabricated index-clearing events. Overflow now emits a distinct `event_loss` record and forces reconciliation; lost history remains unrecoverable. `git_snapshot_transitions_use_real_index_head_and_lock_evidence` tests real fixture staging, commit/HEAD movement, lock and missing-status behavior. A commit is reported as an observed HEAD OID change, not proof of who performed a commit. Native validation remains Linux-only and command/ref transitions between samples can be missed.

The scoped same-user stdio MCP adds read-only `workspace.operations`, `checkpoint.restores` and `submission.reconcile`, for thirteen opt-in no-argument tools total. No restore, cancellation, execution, cleanup, arbitrary path selection or HTTP route is exposed. The actual stdio cross-phase test exercises a new-worktree recovery and queries these records; Python and TypeScript clients also query new views. Scope and Git metadata remain unauthenticated and are not an adversarial filesystem sandbox.

`checkpoint verify` now also checks that the captured raw index parses and exactly matches manifest stages using a temporary index; it explicitly reports submodule and LFS payloads as not verified. Split-index verification remains unavailable rather than a fabricated pass. Fsck plus consistency is not authentication or atomic completeness.

## Bounded 30-step development workflow

`tools/v5_bounded_workflow.py` executes all 30 requested *positions* using five RIT-created worktrees, five RIT-created content checkpoints, RIT submission and candidate, a real conflict simulation, killed-process candidate provisioning, new-worktree subset recovery and MCP. The run completed exit 0 as a **diagnostic workflow**, not as full acceptance: **18 PASS, 8 PASS_PARTIAL, 2 PARTIAL, 2 BLOCKED**. Step 10 produces five explicitly incomplete checkpoints, step 24 only rediscovers/preserves interrupted candidate state (no automatic resume), step 27 clean removal remains blocked, and step 28 is blocked for all workspaces rather than exercising a dirty-specific removal gate. Other partial steps explicitly report incomplete analysis, non-atomic capture and Git integrity versus provenance. Source edits and commits, target advancement and Git fsck are intentional disposable fixture operations; all workspaces, checkpoints, submissions and candidates are RIT-created. Full output and exit code are in the workflow log. This is neither V5 acceptance nor the production 40-step scenario.

`restore_never_overwrites_an_existing_index_lock` additionally injects a concurrent foreign index lock after destination creation, verifies exclusive acquisition refuses it without changing its contents, and verifies the original workspace and index remain unchanged. This is not proof against all same-UID races or every interruption point.

## Git LFS and submodule verification evidence

Checkpoint verification now enumerates captured index gitlinks (object ID and stage) without claiming nested repository or dirty-content availability. It identifies canonical Git LFS pointers among captured regular/staged blob candidates up to 2,048 bytes and reports each pointer's SHA-256, declared size and current local observation. With default storage only, regular local payloads up to 64 MiB are opened descriptor-relatively without following symlinks, streamed through SHA-256, size-checked and re-stat checked. Missing payloads, wrong hashes, unsafe paths, large objects and custom storage are explicit statuses; no LFS executable, filter, network fetch or custom path is followed. Tests cover present, hash-mismatched, missing, symlink and custom-storage cases. This is ephemeral verification, not a guarantee: payloads are **not** retained in checkpoints, unselected/large/malformed content may not be identified, same-user changes remain possible, and no complete submodule or LFS recovery is claimed.
