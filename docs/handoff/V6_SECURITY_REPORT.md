## Why a safe fix is nontrivial

SQLite's rollback journal is required recovery state; deleting, mismatching, or adopting it can corrupt data. Read-only validation cannot perform hot-journal recovery. Schema, application ID, pathname, and a reusable inode are insufficient durable database identity; a manifest stored where an attacker can substitute it is not an independent trust anchor. Path checks before opening do not bind later SQLite sidecar opens. `SQLITE_OPEN_NOFOLLOW` rejects filename symlinks but does not by itself establish database/sidecar identity; `SQLITE_OPEN_EXCLUSIVE` is a no-op for `sqlite3_open_v2`, not exclusive creation. SQLite warns against rename/unlink of open databases, hard links, broken locks and rogue writes. Reference: https://sqlite.org/c3ref/open.html , https://www.sqlite.org/lockingv3.html , https://www.sqlite.org/howtocorrupt.html .

Possible design work, **not an approved implementation**: define attacker, OS identity, trusted root and filesystem assumptions; use protected independently authenticated, crash-durable identity/state and explicit reservation/creation/binding/recovery transitions; prove atomicity/durability across manifest and DB and defend reuse/substitution. Investigate SQLite VFS-level binding for database and all journal/WAL/SHM opens, ownership/type/link/ancestry checks and locking, without aliasing or closing POSIX locks incorrectly. Enumerate each crash window; test an existing hot journal and sidecar races, not merely a fresh database. Same-user attacker resistance needs an actual separate security boundary, not a same-user Git ref. Only remove the gate after independent review and unchanged mandatory tests plus adversarial native tests pass. Never delete an unknown journal/sidecar or writable-open an untrusted DB as a shortcut.

## Platform and release constraints

Linux restricted Git execution is x86-64-specific; no native macOS or Windows secure backend has been established. Windows reparse points require native handle/attribute treatment, not POSIX symlink assumptions: https://learn.microsoft.com/en-us/windows/win32/fileio/reparse-point-operations . On each target, use an isolated native machine and supported filesystem, record OS/filesystem and tool versions, run locked all-feature suites, both mandatory tests, adversarial ancestry/link/substitution/sidecar tests, crash/power-loss recovery, concurrent replacement, and independently review results. Do not change the tests, cleanup journals, or skip the gate to make them pass. Native CI config alone is not evidence of a run.

Protected identity, credentials, authenticated audit/approval, privileged MCP, arbitrary untrusted code execution, queue publication and production release remain disabled. Git refs and workspace manifests are cooperative metadata, not authentication; worktrees are not OS isolation. Non-atomic checkpoint and untrusted extraction/symlink limitations apply even to local preview.
